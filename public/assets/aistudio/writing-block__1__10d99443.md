# البرومبت التنفيذي الشامل لاستكمال مشروع OOZOX قبل الإنتاج

المشروع: https://github.com/marcowaa/oozox-last

الفرع الأساسي: `main`

فرع عمل OTP موجود للمراجعة: `feature/server-side-otp`

أنت مهندس برمجيات رئيسي (Principal Engineer) وفريق Full-Stack وAndroid وBackend وDevOps وQA وأمن معلومات.

مهمتك فحص مشروع OOZOX الحالي بالكامل، وتحديد ما هو مكتمل وما هو جزئي وما هو وهمي/تجريبي وما هو مفقود، ثم استكماله ودمجه واختباره دون هدم أي جزء يعمل.

أنا صاحب المشروع ولست مبرمجاً. اتخذ القرارات التقنية المناسبة بنفسك بعد فحص الكود، واشرح لي فقط القرارات المهمة والخطوات التي لا يمكن تنفيذها دون حساب أو مفتاح أو صلاحية مني.

**لا تتوقف عند التقرير أو الخطة.** بعد مرحلة الفحص ابدأ التنفيذ الفعلي على مراحل صغيرة قابلة للمراجعة، وشغّل الاختبارات والبناء. لا تدّعِ تنفيذ أو اختبار أو نشر شيء لم تنفذه فعلياً.

## 1. قواعد إلزامية

1. لا تعِد كتابة المشروع من الصفر.
2. لا تستبدل Backend الحالي أو قاعدة البيانات أو نظام الدردشة أو تصميم التطبيق لمجرد تفضيلك لتقنية أخرى.
3. لا تحذف ميزة أو شاشة أو بيانات أو مسار API موجوداً ويعمل.
4. لا تكسر التوافق مع بيانات المستخدمين الحالية أو الإصدارات الحالية من التطبيق.
5. لا تنفذ تغييرات قاعدة بيانات مدمرة، ولا تحذف Collections أو Fields قبل وجود Migration وخطة رجوع واختبار توافق.
6. لا تضف مزودين مدفوعين أو خدمات خارجية بلا حاجة مثبتة. قارن التكلفة الحالية من مصادر رسمية قبل الاختيار.
7. لا تضع أسراراً أو كلمات مرور أو API Keys أو Signing Keys داخل Git أو ملفات التطبيق أو السجلات.
8. لا تستخدم بيانات Mock أو OTP تجريبياً في الإنتاج، ولا تترك Backdoors أو Debug Endpoints.
9. لا تعتبر وجود واجهة أو ملف إعداد أو Docker Compose دليلاً على أن الميزة تعمل.
10. عند تعذر الوصول إلى حساب خدمة خارجية أو بيانات اعتماد أو جهاز حقيقي، جهّز الكود والاختبارات والإعدادات، ثم سجّل بوضوح أن التفعيل النهائي يحتاج إجراءً من المالك.
11. لا تشترِ سيرفراً ولا تنشر على خادم حي ولا تغيّر DNS أو بيانات الإنتاج دون موافقة صريحة وبيانات دخول يوفرها المالك. حالياً لا يوجد سيرفر مشتَرى.
12. اعمل في Branch مستقل، مع Commits مفهومة، ولا تدمج إلى `main` إلا بعد الاختبارات ومراجعة التغييرات.
13. قبل تعديل كل ملف افحص استخداماته والمراجع إليه واختباراته. بعد التعديل شغّل الاختبارات المناسبة.
14. لا تضع كل العمل في Commit ضخم؛ استخدم مراحل صغيرة موثقة.

## 4. استكمال Backend والمصادقة والهوية

راجع دورة حياة المستخدم:

- إنشاء الحساب.
- تأكيد الهاتف أو البريد حسب التدفق.
- تسجيل الدخول بالبريد وكلمة المرور أو رقم الهاتف وOTP.
- إصدار JWT والتحقق منه وتجديده وانتهاؤه وإبطاله.
- تسجيل الخروج وإدارة الجلسات والأجهزة.
- استعادة الحساب وتغيير كلمة المرور ورقم الهاتف.
- تأكيد ملكية الهاتف قبل ربطه بالحساب.
- حماية الأدوار والصلاحيات وADMIN والموظفين.
- منع IDOR وPrivilege Escalation.
- حماية بيانات كل مستخدم وشركة من الوصول غير المصرح به.
- التحقق من كل مدخلات API.
- عدم تسريب كلمات المرور أو OTP أو Tokens داخل Logs أو رسائل الخطأ.

### عيوب محددة يجب فحصها وإصلاحها

ظهرت أثناء الفحص الأولي المشاكل التالية، تحقق منها ثم أصلحها:

1. `UserAppPortal.kt` ينشئ OTP محلياً باستخدام `SecurityValidator.generateSecureOtp()` بعد تأخير شكلي، بدلاً من طلب إرساله من Backend.
2. `WhatsAppTelegramOtpView.kt` يقارن رمز المستخدم بقيمة `expectedOtp` داخل التطبيق نفسه، وهذا ليس تحققاً أمنياً.
3. Callback إعادة الإرسال يولّد رمزاً جديداً محلياً.
4. واجهة اختيار WhatsApp وTelegram وSMS لا تعني أن قنوات الإرسال مفعّلة.
5. `OozoxApiService.kt` يحتاج عقود API صحيحة لطلب OTP والتحقق منه وربط Telegram.
6. `authController` كان يصدر JWT مباشرة بعد التسجيل أو نجاح كلمة المرور؛ يجب إعادة تصميم التدفق حتى لا تُصدر جلسة موثوقة قبل تحقق العوامل المطلوبة.
7. `isVerified` في `User.js` ظهر بقيمة افتراضية `true`. افحص أثر ذلك وصححه دون إفساد الحسابات القديمة.
8. لا تسجل جهازاً موثوقاً لمجرد نجاح مقارنة OTP محلية. يجب أن يأتي إثبات التحقق من Backend.
9. افحص `app/build.gradle.kts`: ظهر احتمال رجوع Release إلى Debug Keystore عند غياب مفتاح التوقيع. امنع ذلك واجعل بناء Release يفشل برسالة واضحة عند غياب مفاتيح الإنتاج.

### تصميم تدفق المصادقة

- لا تكسر تسجيل الدخول بالبريد وكلمة المرور إذا كان مستخدماً.
- اجعل OTP مطلوباً للعمليات التي تحتاج إثبات ملكية الهاتف أو تسجيل الدخول بالهاتف أو الدخول من جهاز جديد وفق سياسة موثقة.
- كل خطوات التحقق وإصدار JWT في Backend.
- التطبيق يعرض الواجهة ويرسل الطلبات ويستقبل نتيجة الخادم.

أنشئ API Contract موثقاً، مثل:

- `POST /api/otp/request`
- `POST /api/otp/verify`
- `POST /api/otp/telegram/link/start`
- `POST /api/webhooks/telegram`
- مسارات Auth النهائية التي تكمل التسجيل أو الدخول بعد إثبات OTP.

عدّل شكل المسارات إذا لزم، لكن اجعل Android والويب يستخدمان نفس العقد. لا تُصدر Access Token كاملاً من تأكيد رقم الهاتف وحده قبل إكمال التسجيل أو الدخول المناسب.

## 5. تفعيل OTP عبر SMS وWhatsApp وTelegram

### SMS وWhatsApp

قيّم Twilio Verify أو مزوداً آخر مناسباً. تحقق من الأسعار الحالية لمصر والدول المستهدفة ومن متطلبات WhatsApp Business وموافقات القوالب وحالة الحساب من المصادر الرسمية.

لا تفترض أن تفعيل SMS يعني تفعيل WhatsApp.

### Telegram

استخدم Telegram Bot API. يجب أن يبدأ المستخدم محادثة مع البوت بنفسه أو يربط حسابه عبر Deep Link آمن بعد إثبات ملكية الهاتف بقناة موثوقة.

لا تحاول إرسال رسالة لمستخدم لم يربط حسابه ولم يبدأ البوت.

### ضوابط OTP الأمنية

- توليد الرموز على الخادم فقط باستخدام CSPRNG.
- Twilio Verify أو المزود المعتمد يدير رموز SMS وWhatsApp والتحقق يتم من الخادم.
- Telegram OTP يولد على الخادم ويحفظ كـ HMAC/Hash غير قابل للاسترجاع ويرسل إلى Chat ID المرتبط.
- صلاحية قصيرة قابلة للضبط.
- رمز أحادي الاستخدام.
- محاولات محدودة وResend Cooldown.
- Rate Limit على IP ورقم الهاتف والجهاز والحساب، ويفضل عبر Redis.
- منع تعداد أرقام الهواتف قدر الإمكان.
- إلغاء التحديات القديمة.
- منع نجاح استخدام الرمز مرتين حتى مع الطلبات المتزامنة.
- عدم حفظ OTP أو أسرار المزود في Logs.
- Webhook Telegram محمي بسر Webhook Header ورابط ربط أحادي الاستخدام محدود المدة.
- لا تعرض مفاتيح Telegram أو Twilio في التطبيق.
- Fail Closed: عند غياب إعداد المزود أرجع خطأ واضحاً ولا تنشئ OTP وهمياً ولا تسمح بالدخول.

أضف متغيرات بيئة موثقة مثل:

- `OTP_HMAC_SECRET`
- `OTP_TTL_SECONDS`
- `OTP_RESEND_COOLDOWN_SECONDS`
- `OTP_MAX_ATTEMPTS`
- `TWILIO_ACCOUNT_SID`
- `TWILIO_API_KEY_SID`
- `TWILIO_API_KEY_SECRET`
- `TWILIO_VERIFY_SERVICE_SID`
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_BOT_USERNAME`
- `TELEGRAM_WEBHOOK_SECRET`

لا تضع أي قيمة سرية حقيقية في Git. حدّث `.env.example` وDocker Compose وDeployment Script وRunbook دون تغيير مفاتيح التشفير القديمة.

## 10. التحكم في التكلفة والميزانية

أضف إعدادات قابلة للتعديل من لوحة الإدارة:

- ميزانية شهرية للمكالمات.
- تنبيه أول عند نسبة يحددها المدير.
- تنبيه ثانٍ عند نسبة أخرى.
- حد أقصى لمدة المكالمة.
- حد يومي لاستخدام كل مستخدم.
- حد يومي/شهري للفيديو.
- تفعيل وتعطيل الصوت والفيديو وفق السياسة.
- صلاحيات بحسب المستخدم أو الدور.
- استثناءات إدارية موثقة.
- منع المكالمات الجديدة أو إصدار Tokens عند بلوغ الميزانية.
- عدم قطع مكالمة جارية فجأة إلا بسياسة صريحة وآمنة.

مثال توضيحي وليس إعداداً ثابتاً: ميزانية 1,000 جنيه، وتنبيه عند 50% و80%، وتقييد المكالمات الجديدة عند 100%.

يجب أن توجد حماية فعلية في Backend، لا مجرد تنبيه. احسب التكلفة من أسعار المزود الفعلية وسعر الصرف الموثق وتاريخ التسعير. وضّح أن التكاليف تقديرية إن لم يقدم المزود بيانات لحظية.

## 11. محاسبة مدة المكالمة

- لا تبدأ الحساب عند طلب الاتصال أو الرنين.
- ابدأ عند قبول الطرف الآخر وبدء الاتصال الفعلي حسب Event موثوق.
- سجل وقت البداية والنهاية والمدة الفعلية.
- لا تحتسب الرنين.
- عالج انقطاع الإنترنت وإعادة الاتصال.
- لا تثق بمدة يرسلها Android أو Web.
- امنع تكرار التسجيل أو المحاسبة (Idempotency).
- استخدم Webhooks أو Provider Events موثوقة مع التحقق من التوقيع ومنع Replay.
- اجعل البيانات قابلة للربط مستقبلاً بالمحافظ أو النقاط أو الدفع.

## 12. التنبيهات والمراقبة

استخدم نظام الإشعارات الموجود إن كان صالحاً.

أرسل تنبيهات إدارية عند:

- بلوغ نسب الميزانية.
- ارتفاع الاستهلاك غير الطبيعي.
- ارتفاع فشل المكالمات.
- مشكلة مزود RTC أو Webhooks.
- زيادة المكالمات النشطة بصورة غير معتادة.
- استهلاك مستخدم بصورة غير معتادة.
- الاقتراب من الحدود اليومية والشهرية.
- فشل OTP Provider أو سلوك OTP غير طبيعي.

أضف Health Checks وStructured Logs وMetrics مع إخفاء الأسرار والبيانات الحساسة.

## 13. بقية وحدات المشروع

لا تحصر العمل في OTP والمكالمات. افحص وأكمل الوحدات الفعلية:

- المستخدمون والأدوار والصلاحيات.
- الشركات والملفات التجارية.
- الموظفون والموارد البشرية والرواتب والحضور.
- الفواتير والحالات والمدفوعات والتقارير.
- المهام والمشاريع ومجموعات العمل.
- الإشعارات وFCM.
- الدردشة والمحادثات والوسائط.
- Offline/Online Sync وحل التعارضات.
- النسخ الاحتياطي والاستعادة.
- اللغات والتوطين وRTL.
- خدمات AI والإعدادات المرتبطة بها.

لكل وحدة:

1. قارن الواجهة مع API.
2. تحقق أن كل زر يؤدي وظيفة فعلية.
3. تحقق أن Backend يطبق Validation وAuthorization.
4. تحقق من ملكية البيانات وعزل المستخدمين والشركات.
5. أضف أو أصلح API عند الحاجة فقط.
6. أضف اختبارات Unit وIntegration.
7. أصلح Mock/Placeholder في الإنتاج.
8. حافظ على الميزات العاملة.

## 14. قاعدة البيانات والترحيلات

- راجع جميع Mongoose Models وIndexes وReferences وEncryption.
- أضف Models وIndexes لـ OTP وPhone Identity وTelegram Linking وCall Logs وUsage/Budget حسب الحاجة.
- لا تخزن OTP كنص صريح.
- لا تخزن Secrets أو Provider Tokens في Documents مكشوفة.
- استخدم TTL Indexes عند الحاجة، لكن تحقق من `expiresAt` في التطبيق؛ حذف TTL ليس فورياً.
- افحص الفهارس الفريدة على الحقول nullable وتأكد من عدم تعارضها مع البيانات القديمة.
- أنشئ Migrations قابلة لإعادة التنفيذ قدر الإمكان واختبرها.
- لا تغير `DB_ENCRYPTION_KEY`، فقد يؤدي ذلك إلى فقدان إمكانية فك بيانات قديمة.
- اختبر Backup وRestore فعلياً في بيئة اختبارية.

## 19. التواصل مع صاحب المشروع

لا تكثر من الأسئلة التقنية. اتخذ القرارات الممكنة من الكود بنفسك.

اطلب مني فقط ما لا يمكن اختلاقه أو تنفيذه دون مالك الحساب، مثل:

- حساب Twilio أو مزود الرسائل.
- تفعيل WhatsApp Business/Verify والموافقات اللازمة.
- إنشاء Telegram Bot عبر BotFather.
- حساب مزود RTC إن احتاج خدمة خارجية.
- Firebase Project و`google-services.json` عند الحاجة.
- الدومين وDNS والبريد الخاص بـ SSL.
- شراء VPS وعنوانه وطريقة SSH عند مرحلة النشر.
- Android Release Keystore.

لا تطلب مني وضع كلمات المرور والأسرار داخل Git أو المحادثات. وضّح أين أضيفها في Secret Manager أو Environment Variables.
